用户能进 JumpServer，也看得到资产，连网站时却报 500。当时 12 个业务容器都是绿的。这个问题后来是顺着连接分配查出来的。装机、目录组同步和 Agent 的测试也记在这篇。

2023 年写过一篇[《JumpServer 单节点无外置数据库部署》](/2023/10/18/Jump%20server单节点无外置数据库部署/)，讲的是一套环境怎样装起来。这次我负责的是团队访问链路的日常运行，涉及目录组同步、会话诊断、备份和恢复。最后才接上 Agent 做资产查询与试点纳管。

JumpServer 企业版 4.10 装在一台虚拟机里。员工用目录账号登录，选有权访问的资产，接入组件用对应协议连过去。后面查 500 时，我按这个顺序找，先看哪一步已经走过。

```text
用户 → JumpServer 登录（LDAP）→ 查询组织与资产授权
     → 选账号和协议 → 接入组件代连目标 → 会话审计

Agent → 独立 API 身份 → 查询对象或提交变更
      → 审批后的执行身份 → 回读平台与连接证据
```

## 单节点能解决什么，哪类故障要另留退路

给现有部署列几类故障，分别确定由哪一层恢复。

| 故障 | 对策 |
| --- | --- |
| 容器挂了 | Docker 自动恢复策略 + 组件级 `jmsctl restart`，不做整栈循环重启 |
| 数据库坏了 | 每日 pg_dump 原子备份 + 升级前强制 dump + 按时间戳命名的回退点 |
| 宿主机或盘故障 | 独立存储目标上的备份，并用隔离环境演练恢复 |
| 没人知道它病了 | 两分钟粒度健康巡检，状态原子落盘，接 Zabbix，失鲜也告警 |
| 升级升不上去 | 升级前必须有 dump；回退路径事先走通过一次 |

备份拷出来后先试着读一遍。换到一台干净机器还能不能恢复出登录、连接和录像，要另找时间演练，异地副本也得实际取回来一次。

## 承载与运维通道

### 虚拟机设计

| 项 | 值 | 说明 |
| --- | --- | --- |
| 承载 | PVE 单节点上的一台 VM | 宿主机单节点无 HA，风险已标注 |
| OS | Ubuntu 26.04.1 LTS | ostype `l26` |
| 网络 | 单网卡入 VLAN，与业务平面隔离 | 堡垒机流量与业务流量分 VLAN |
| 存储 | 虚拟磁盘落 ZFS | 备份目标独立评估故障域 |
| 虚拟机管理 | 保留受审计的宿主侧救援入口 | 日常访问走独立运维身份 |
| 开机自启 | 启动链内 | 宿主机重启后自动恢复 |

### 堡垒机自己的救援入口

堡垒机断开时，管理员还要能拿到日志、读出服务状态并处置故障。给它预留一条经虚拟化管理面的救援路径。宿主侧操作继承虚拟化管理面的高权限，单独管授权与审计。Agent 的应用访问身份和日常巡检身份都不复用这条路径。

### 从启动容器到接入第一台测试机

这套部署可以先在一台授权测试机上复现。确认虚拟机时钟、DNS、存储容量和维护入口后，按同一发行版的安装器拉起组件。Web 能登录时，用测试用户进组织，检查它能否看到指定资产并用约定账号打开会话。连接结束后到审计台找记录。这个样本能跑通，再加第二种协议和目录同步，出错时比较容易判断是公共入口故障还是单条连接链的问题。

网络的回验按方向做。客户端到 Web 和协议入口、协议入口到目标、应用到目录服务。测试源也要选对，从堡垒机宿主访问到预期目标，与真实用户从办公网连接是两条证据。生产入口要按组织要求验证 TLS、证书链和管理可达性，文中的安装记录不能替代这些验收。

## 版本选型：一次失败升级教会的事

时间线：

1. 初装社区版 4.10.19
2. 试用企业版，生产稳定在 v4.10.18-ee
3. 2026-09 一次 v5.0.0 升级尝试，两周内判定失败，回退 ee

当时借助升级前的数据库归档做了回退。单次回退能恢复原版本，完整环境仍需独立恢复演练。后来把可重复核对的部分拆成了三项：

- **升级前留存可识别的备份和版本记录。** 先查归档生成结果，再验证目录可读。同时记录数据库、应用配置、密钥恢复材料与会话存储范围，单个数据库包不足以覆盖整套环境。
- **回退路径必须事先走通一次**。我们这次是「恰好」回退成功，不算验证；验证标准是回退演练过
- **升级残留要当故障源管理**：v5 的 `kael` 容器停在 Exited、1.4 GB 的安装包和解压目录留在 `/opt/`——只要残留还在，下次误操作就可能二次翻车。残留不删，升级就没结束

另一个教训是**版本事实要验容器不信目录名**。`/opt/` 下同时有三个版本的目录，真实生产版本只有一个判定依据：

```bash
docker ps --format "{{.Names}}|{{.Image}}" | grep -vE "postgres|redis"
# 期望全部是 jumpserver/*:v4.10.18-ee
readlink /opt/current/installer   # 软链指向才是 jmsctl 实际使用的安装目录
```

## 组件与网络设计

13 个容器，四个业务面：

| 面 | 组件 | 端口 | 用途 |
| --- | --- | --- | --- |
| Web | web / core / celery | 80 | 前端 + API + 异步任务 |
| 协议网关 | koko / razor / xrdp / lion | 2222 / 3389 / 3390 / 4822 | SSH、RDP、Linux 图形、图形转发 |
| 数据代连 | magnus | 33061-33062 / 54320 / 15210 / 14330 / 27018 / 63790 | MySQL、PostgreSQL、Oracle、SQL Server、MongoDB、Redis |
| 内置存储 | postgresql / redis | 仅 127.0.0.1:5432 / 6379 | 数据库与缓存 |

网络取舍两个：

- **业务接入与数据库管理分开。** 业务侧通过 JumpServer 提供的访问入口连接资产。维护数据库走受控管理路径。验收时分别核对容器内监听、宿主端口发布与业务网可达性。
- **容器网段 `DOCKER_SUBNET` 独立成段**，与业务网段、宿主网段都不重叠。跳板机的容器内部网络是最容易被当成「反正不对外」的地方，出问题时反而最难查——独立网段让 `ip route` 一眼分清内外。

## 备份、巡检、目录同步与日志轮转

日常备份、巡检、部门同步和日志轮转各有独立计划与回退对象。巡检另外核对本轮采样时间，避免读到上一次留下的绿灯。

### 1. 每日数据库备份（`jms-daily-backup.timer`，每日 03:10，漏跑补跑）

归档先写入备份目标目录中的临时文件。确认 `pg_dump` 成功，并用 `pg_restore --list` 读出归档目录，再在同目录改名发布。磁盘写满或数据库连接中断时，让作业报错，保留上一次有效备份。

```bash
umask 077
staging_file=$(mktemp "$backup_dir/.jumpserver-XXXXXXXX") || exit 1
archive_file="$backup_dir/jumpserver-$(date -u +%Y%m%dT%H%M%SZ)-${staging_file##*-}.dump"

if pg_dump --format=custom --file="$staging_file" jumpserver &&
   pg_restore --list "$staging_file" >/dev/null; then
    mv -- "$staging_file" "$archive_file"
else
    printf '%s\n' '备份写入或归档目录检查失败' >&2
    exit 1
fi
```

备份目标目录限制为备份账户访问。归档目录可读只完成第一道检查，数据、所需密钥和应用状态仍要在隔离环境里做恢复演练。失败暂存按备份作业的保留策略处理，不参与有效备份轮转。[PostgreSQL 的归档目录说明](https://www.postgresql.org/docs/18/app-pgrestore.html)

### 2. 两分钟健康巡检（`jms-health.timer`）

巡检不是 `docker ps` 看一眼就完事，检查项分四层：

| 层 | 检查项 |
| --- | --- |
| 容器 | 12 个业务容器健康状态 |
| 数据 | PostgreSQL 可查询、Redis 响应 |
| 入口 | Web 健康接口、RDP 发布机 3389、启用中的远程应用是否有成功发布与在线发布机 |
| 自身 | 每日备份的时效（昨天有没有跑成）、日志属主、轮转失败状态 |

两个关键机制：

- **状态原子落盘**：结果写 `/var/lib/jms-health/current.json`，原子替换。下游（Zabbix、值班脚本）读到的永远是完整文件，不会出现读到一半的状态
- **失鲜独立告警**：健康值的采样时间戳单独一个 Zabbix 对象，**文件停止更新本身就是告警**——巡检挂了比业务挂了更可怕，因为它让你以为业务还活着

Zabbix 侧四个对象：原始状态、健康值、采样时间戳，再加异常与失鲜两条告警规则。失鲜规则盯时间戳不盯数值，专治「旧文件假绿」。

### 3. LDAP 登录和部门映射分两层

JumpServer 通过 LDAP 对接目录，登录范围由 Base DN 与过滤条件限定。先用测试账户核对启用、禁用和迁移部门三种情况。Base DN 过窄会漏人，过宽则可能带进服务账号和无关组织。

部门权限单独同步。脚本读取目录状态，按映射表计算受管用户组的期望成员，再与 JumpServer 现状比对，只写差异。只允许改清单中的业务组，系统组保留原状。移出部门和离职需要走不同的管理流程，不能把定时同步的时间窗口当成即时撤权。

举个脱敏例子。一个人从开发组转到质量组，登录身份可能保持不变，变化的是两个受管组的成员关系。同步要同时算出旧组移除、新组新增，写完回读两组。能否看到目标资产还要看质量组对应的资产授权。反过来，目录查询超时应记为没有拿到输入，不能把空结果当作组织里没人。

我用相同的目录快照重复执行过同步，结果保持一致。每轮先看增删清单，再回读实际组成员；如果目录查询失败，保留当前授权，避免把查询故障误当成全量删人。

### 4. 日志轮转收口

加固前日志轮转规则重复且属主混乱，rsyslog 新旧规则打架。收口方式：保留发行版 rsyslog 规则的 12 份轮转与 50 MiB 阈值，旧重复规则改成说明文件归档，新规则指定 `syslog:adm / 0640`，修正现存日志属主，`logrotate -d` 调试加实跑双验证，全程不重启日志服务。**合并前先确认没有业务在依赖旧规则的轮转间隔**——这条比改配置本身容易踩坑。

## 登录正常却连不上，怎样定位那次 500

登录和资产列表都能用，只有部分网站资产的连接选项返回 500。巡检当时看到 12 个业务容器健康，也没有内存耗尽的迹象。这个组合能排除明显的整栈停机，定位应从该协议经过的组件往下走。

沿着连接分配查下去，找到一条还启用着的旧应用记录，底下已经没有可用的发布实例。我只停用了它。连接选项回来以后，又从浏览器进去、正常退出，再去审计里找这次的会话 ID，找到了约 1.8 MB 的归档录像。做到这里，才知道用户的操作和录像都回来了。

巡检因此还要看已启用的连接方式是否具备有效发布目标。容器探针继续保留，历史离线记录和现有用户连接失败分别统计，否则升级后的遗留记录会遮住真实故障。

## Agent 能读什么、能改什么，怎么验收

这里有两种工具。Codex 调 JumpServer API 管资产、账号和权限，也能查审计。远程执行工具用指定机器的 OS 账号登录，装软件、改配置和升级都在这一侧做。拿一台新服务器来说，API 可以把它登记给研发组，操作系统这边还得检查用户连到的是哪台机、要交付的服务起了没有。

### Codex 怎么调用 JumpServer API

API 请求用服务账号的 Access Key 做签名。Codex 选要调用的操作，把组织、目标对象和这次允许修改的字段交给工具。签名由工具完成，密钥留在凭据入口。能调哪些接口，要看实例版本、系统角色和目标组织里的角色。日常查资产用只读身份就够了，给机器入库或改授权，再用拿到对应权限的执行身份。[API 认证](https://docs.fit2cloud.com/jumpserver/v4/dev/rest_api/) · [角色列表](https://docs.fit2cloud.com/jumpserver/v4/manual/admin/system_settings/role_list/)

| 我交给 Codex 的事 | 在 JumpServer 查或改什么 |
| --- | --- |
| 盘点一批服务器 | 按组织、节点查资产的平台、协议和已登记的账号 |
| 查谁能连一台机器 | 查组成员和命中的授权，列出登录账号、协议、动作和有效期 |
| 纳管服务器或收回访问权 | 新增或更新资产、登记资产账号，按需绑定或撤掉本次授权 |
| 查一次失败的连接 | 按资产与时间查会话，再查角色有权查看的活动、作业或录像 |

实际遇到「我转到质量组了，怎么还是看不到机器」，我会先让它查目标组织和 LDAP 同步后的组成员，再看资产授权引用的是组、节点，还是直接绑了个人。若目录侧的组关系还没同步过来，直接给人加权限会在平台上多留一条规则。以后这个人再转组，那条规则依然可能有效。查现有权限时我会让它把规则来源列出来，账号只返回标识和所属资产，口令交给连接工具使用。

会话能查到用户、资产账号、协议和起止时间。在支持终止会话的入口上，我确认要断的会话 ID 和影响，再用有相应权限的身份处理，并重查会话状态。回看录像也要有审计权限。API 能记下某条规则写成什么，实际连接记录则用于核对谁真的连过机器。[会话记录](https://docs.fit2cloud.com/jumpserver/v4/manual/admin/audit/session_audit/session_record/) · [系统任务](https://docs.fit2cloud.com/jumpserver/v4/manual/admin/system_settings/system_tasks/)

例如「把一台测试机给研发组用到周五」。我给出组织、机器、研发组和准许使用的登录账号。Codex 先查有没有这台资产，列出将新增或沿用的资产、账号和授权，以及允许的协议和期限。资产名相同但归属或地址对不上的，先把两条记录拿出来给人确认。已有资产时，沿用查到的 ID，单独确认绑定哪个登录账号，再建规则。

接口超时就找刚才那份对象或规则，确认当前状态再决定是否重试。碰到权限拒绝，把对象、动作和拒绝原因记清楚，交给对应管理员确认。写完按资产 ID、账号和规则 ID 回查一遍，最后用组里的测试用户实际连接，确认登录的是预定机器和账号。收回时再测一次这个用户的新连接。旧会话是否还在、用户是否从其它规则仍然有权访问，分别核对。[资产账号](https://docs.fit2cloud.com/jumpserver/v4/manual/admin/console/account_management/account_list/) · [资产授权](https://docs.fit2cloud.com/jumpserver/v4/manual/admin/console/authorization_manage/assets_authorization/)

### 给到 OS 账号后，可以接手什么

给到指定机器的用户名和密码后，连接工具沿批准的入口登录。第一趟我先读主机标识和当前用户，接着看系统版本、服务、日志、磁盘和备份，确认这个账号实际能读到哪。能做维护的账号，在批准范围内可以装软件、打补丁、写配置、启停服务、备份和恢复。JumpServer 决定这次连接能用什么资产账号和协议，命令的权限仍按主机上的账号算。密码由工具在登录时使用，操作记录只留目标、身份用途和结果。

改一项服务配置时，我会让它拿到文件原值和服务当前实际用的值，再决定怎么改。需要重启的话，在变更里把影响和恢复旧配置的办法先写好。执行后除了查进程和配置，还要用原来会走这台服务的请求试一次。遇到连接断开，回来先查文件、进程和业务状态，确认上次到底做到哪，必要时按已有回退步骤处理。

如果一台新服务器连操作系统账号也没准备好，我先确认哪一方负责创建。已有可用 OS 账号时，用它核对机器和服务，再登记到 JumpServer。需要新建账号时，由获准管理这台服务器的身份在系统里创建，再依授权绑定到 JumpServer。平台里那条账号记录有没有写对、目标机能不能用这对凭据登录，要分别试。

### 给 JumpServer 本身升级

升级时登录的是跑 JumpServer 的 Linux 主机，用它的维护账号。Codex 可以先读版本、部署方式、组件、磁盘和进行中的会话，再核对本次安装包、版本路径和回退条件。我会在窗口前确认备份能取回来，范围里包含数据库、恢复需要的配置和密钥材料，以及单独存放的录像等数据。必要的救援入口也提前试通，否则堡垒机停了以后，远程维护可能一起中断。

到了窗口，按已经确认的版本路径，用安装器支持的升级方式执行。启动后核的是运行中的版本和组件状态。接着用测试用户登一次，在堡垒机上连一台代表性的资产，再查这次的会话和应有的录像。中途报错时，先留出错阶段、日志和数据库是否已迁移的状态，再按窗口约定处理回退。经堡垒机的连接按实际协议和录制配置找审计。走救援入口时，命令结果和时间记到该通道自己的变更记录里。[单机升级指南](https://docs.fit2cloud.com/jumpserver/v4/installation/setup_linux_standalone/offline_upgrade/) · [备份和恢复](https://docs.fit2cloud.com/jumpserver/v4/installation/backup_recovery/)

这次实际跑通的是用签名 API 创建测试对象、授权、回读和清理。前面那次 500 另有一次真实的浏览器连接，退出后按会话 ID 查到了录像。把收紧权限后的服务身份、申请、执行、撤权和失败恢复接到同一次演练里，还要再跑一轮。

## 给接手的人留下哪些证据

回退优先按对象恢复。变更前留存目标对象的标识和原值，出问题只撤回本次改动。整库回退会覆盖备份点以后其他人的正常变更，需要独立审批并先评估影响。

已经验证的是数据库备份可读、巡检状态可以采集、部门映射可重复执行，以及网站连接恢复后可以读回录像。完整恢复、告警实际送达、授权自动回收和 Agent 收权后的全流程仍需单独演练。备份可读只覆盖备份格式，不能替代恢复到干净环境并验证登录、连接、录像与密钥可用。

把故障交给下一班时，我会给出变更号、授权对象和实际会话 ID。这样他能自己点开那段连接或录像，知道用户是不是用上了。需要撤回时，再从记录里找旧配置和当时还没验证完的项。
