Home Assistant 面板可以进，几个实体一直是旧值。Agent 最初只查应用接口，每次都报「不可用」。排这类问题，我会先记下实体和最后一次上报时间，再找那段时间的设备消息和进程日志。

这套安装跑在 Home Assistant OS 上。Core 负责自动化和实体状态，Supervisor 管理应用与系统更新，HAOS 是下层操作系统。我先用应用 API 确认哪些实体受影响，再去对退出时间和日志。这里的「集成」指用户看到的一项功能；只有功能确实依赖单独运行的应用，查对应容器才有意义。一般集成的错误也可能只出现在 Core 日志里。

## 从「不可用」查到进程退出

日常读实体状态、事件和可用性走 Home Assistant 支持的应用接口。需要确认磁盘用量、容器状态或系统升级结果，再用受限管理路径查系统。系统级权限只留给明确需要的任务，升级和其他高权限变更由人工批准。

实体和进程的时间对上了，接着看日志。有的明确写了内存不足，有的只是升级时退出。应用接口已经能答的事，就在应用这边查。

容器退出码 `137` 表示进程因 `SIGKILL` 退出。要判定是 OOM，还要核容器的 `OOMKilled` 状态和对应时间段的内核日志；停止超时后被强制终止也会出现同一个退出码。其他非零退出码按应用自己的日志解释。比见到异常就重启多一步，但能决定下一步是查内存、退出流程，还是配置。

| 应用侧现象 | 下一步读什么 | 如何判定恢复 |
| --- | --- | --- |
| 单个集成不可用 | 相关应用的退出状态和同一时间段日志 | 恢复动作后，实体重新上报有效值 |
| 多项操作都变慢，且备份开始失败 | 磁盘使用量，再分开看数据库、备份和容器日志 | 找到占用来源，复查剩余空间及相关操作 |
| 系统更新后设备卡在旧状态 | OS 版本、Supervisor 管理的应用状态、关键实体的最近更新时间 | 对照更新前的基线，单独记录仍未恢复的对象 |

磁盘告警最容易处理错。总用量只能说明快满了，不能告诉我是不是该动备份。先找增长的是日志、数据库还是归档，再用各自支持的保留策略处理。否则删几份备份或许能把红色告警变绿，实际增长源和恢复风险都还在。

另外踩过一次容器内临时改文件的坑：当时看着生效，升级替换容器后，改动就没了。后面的变更只走 Home Assistant 支持的持久化配置入口，容器内部留作诊断现场。

## 备份、升级和读证据

HAOS 和 Home Assistant Core 分开更新。HAOS 支持从界面或 CLI 更新，我这次用 CLI，方便在同一条记录里对比升级前后的版本和状态。步骤是先建备份、确认归档能读，再升级，最后核 OS 版本、相关应用和关键实体。版本对上只是升级生效，关键实体重新出数才算应用层恢复。

升级审批前后，我用 `ha os info` 对照 OS 版本，在备份清单 `ha backups list` 里核对本轮备份标识。备份登记、备份文件可读取、系统更新后实体重新上报，三条各记一笔，后续排查才知道该从哪一步补证据。

传文件时还有个容易记反的细节：新版 OpenSSH 的 `scp` 默认使用 SFTP，`-O` 是改用旧 SCP 协议。只有确认目标端不支持 SFTP、同时允许旧 SCP 时，才需要考虑这个兼容选项。

我在现场先拿本次备份的标识，再用两次间隔约 8 秒的大小采样判断要不要继续等。这个采样只是提示写入可能结束，归档传回后还做了结构检查。换成通用流程时，应以平台可见的备份状态和归档检验判断备份是否完成；旧备份的轮转也应看本次是否已有可用副本，别把用户手动备份算进去。

升级后最容易看错的是那些平时就不动的实体。界面上的旧值还在，先选一个能出新事件的实体，等它真的上报，再把时间记下来。磁盘和进程告警也沿用这个办法，先找具体变化，再看它对应哪一段日志。

归档结构检查通过，是这一轮的最后一项备份证据。升级仍由人工确认，升级失败后的恢复演练还没有完成；如果要进一步放开自动升级，先补一个能实际装回配置、验证关键实体再上报的独立恢复环境。

公开材料里也没有一条带时间戳的实体恢复原始记录。留下这类时间线时，我会用同一个脱敏实体代号，把下面三项对齐到同一时区，再判断它缺了哪层证据。尤其最后一项要等到处置之后的新消息，旧状态还能读到并不满足条件。

| 顺序 | 该记哪条证据 |
| --- | --- |
| 应用侧发现异常 | 第一次读到不可用的时间、最后一次有效上报时间 |
| 系统侧定位 | 相关进程的状态变更时间、退出状态和同一时窗的日志 |
| 回到应用侧验证 | 新上报的时间和有效状态，连同本次操作完成时间 |
