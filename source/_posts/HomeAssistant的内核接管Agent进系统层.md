Home Assistant 在接管清单里是特殊的：它的官方 API 很完善，但那些 API 全是应用层的——实体、自动化、配置。Agent 要处理"某个集成容器挂了"、"系统盘快满了"、"升级 HAOS 本身"这类问题，全在 API 外面。

这篇记录把 HAOS 改造成 Agent 可接管形态的做法，核心是把**应用层（REST/WebSocket API）**和**系统层（SSH 进 HAOS 内核）**两个通道分开建，各管各的，不混用。

## 两个通道，各管一段

| 层 | 通道 | 覆盖 | 权限 |
| --- | --- | --- | --- |
| 应用层 | REST + WebSocket API | 实体、自动化、集成配置、日志读取 | 长期 token，只读为主 |
| 系统层 | SSH 进 HAOS 内核 | 容器管理、系统包、磁盘、内核参数、HAOS 升级 | 域内限定，root |

应用层通道从装完就有：长期 access token 建在专门的服务账号上（不是主账号），scope 按"读多写少"给。Agent 日常巡检走这一层：实体状态、集成健康、最近事件，全不碰系统。

系统层通道是这次新开的。HAOS 的 SSH 默认不开，开了就是 root，这个权限级别在家庭环境里需要配套收口动作（后面讲）。

## 系统层能干什么：三类真实任务

接管跑通之后，Agent 通过系统层实际处理过三类任务，列出来说明这个通道不是白开的。

**容器故障。** 某个第三方集成以容器方式跑，崩溃后应用层只看到"集成不可用"，看不出是容器 OOM 还是镜像挂了。系统层 `docker ps -a` + `docker logs --tail` 一步定位，重建容器比从 UI 里"重新配置集成"快得多，也不动配置。

**磁盘水位。** HAOS 系统盘不大，数据库加备份慢慢会涨。Agent 定期查 `df`，水位过线时先查占用大头（`/var/lib/mysql`、备份目录、容器日志），容器日志的轮转策略在系统层改一次就长期生效，不用每次手动清。

**HAOS 升级。** 应用层 UI 只能选"升级 HA"，HAOS 本体的升级要走系统层。Agent 的做法是：升级前读当前版本号、确认磁盘余量、拉一个快照；升级后对比版本号、检查各集成状态、把结果写回巡检报告。整条链路里没有一步需要人打开 UI。

## 容器内操作：不要从内核钻

HA 本体是一个容器，第三方集成容器也是容器。这里有一个容易走偏的做法：从 HAOS 内核里 `docker exec` 进 HA 容器改文件。能成，但 HA 升级时容器是整体替换的，改的文件没了，而且应用层的配置机制（`configuration.yaml`、UI 配置）会被绕过，出问题时两头查。

收口的规则：**容器内的配置变更一律走应用层 API 或配置文件挂载；系统层的 `docker exec` 只用于诊断，不用于修改**。诊断产出的是日志和状态，修改必须走会被升级保留的路径。

## 权限收口

SSH root 在家庭网里的风险面主要是"谁能连"。收口动作：

- 端口只放行管理网段（与 Windows 侧同一个限定逻辑）；
- 主用密钥登录，口令登录保留但走独立于统一密码的单独口令（HAOS 对统一口令不认，这事本身就说明了它是独立系统）；
- Agent 每次系统层操作在报告里标注"系统层"，与应用层操作区分——权限级别不同，出问题的排查路径也不同。

## 与整站接管的关系

HA 这条线打通后，家里的接管面覆盖了：Windows 主机（WinRM）、Linux 服务机（SSH）、HAOS（SSH 系统层 + API 应用层）、Web 控制台服务（各自的 API，下一篇）。Agent 侧的结论是统一的：**每个系统给出"应用层 + 系统层"两个明确通道，操作分级，不靠一个万能通道走天下**。

**遗留未闭环**：HAOS 的自动升级策略没有完全交给 Agent，目前是"Agent 巡检提示 + 人工确认执行"。全托管的前提是升级失败的回滚演练过，这一步还没做。
