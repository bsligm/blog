一次补丁窗口后，Zabbix 的版本查询超时，但再查服务状态没看到有用的新信息。我转去看 systemd 作业队列，才发现数据库和监控服务的启动动作还在等待。此时反复发启动命令，只会让排查更乱。

那次把已阻塞的作业处理完后，我重跑了一开始超时的同一个版本查询，确认 API 恢复响应。这一步验证的是接口可用，采集恢复还应看监控数据有没有继续更新。文章保留这两项验收的区别，免得把进程状态或 API 有响应当成整个业务已恢复。

## WAF 的拒绝单独处理

另一次升级后，控制台能打开，但管理 API 返回 `403`。同一产品的页面会话和管理接口可以有不同授权边界。先保留失败请求的时间、状态码和版本信息，确认受影响的是哪类管理请求，再检查该版本的文档和已有授权。权限异常在当时只定位到管理面，业务转发和规则生效仍需各自验证。把这个限制写进巡检结果，避免把拒绝直接归成实例宕机或跳过检查。

## 日常巡检留下的四个字段

这两个故障之后，我给每项服务留下四条记录：

| 字段 | 平时怎么用 |
| --- | --- |
| 探活请求 | 选一个低成本、无副作用的请求，能说明该接口确实在响应 |
| 深查入口 | 查日志或系统作业队列，写清什么时候需要人接手 |
| 变更证据 | 保存变更前后状态，必要时用实际业务请求再核一次 |
| 授权范围 | 标清只读与可写操作。公网策略、证书、配额等变更保留人工审批 |

Agent 平时把探活失败的服务列出来，带上对应的系统层状态和最小证据，省去逐个打开控制台翻记录。权限和凭据跟着服务授权走，巡检输出只留状态与必要上下文。这个做法适合定期巡检，当时还没有建设统一的服务层实时告警。因此故障可能先发生、下一轮才被发现，表里的检查结果也只对记录的时间窗口负责。
