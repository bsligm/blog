Steam Deck 上跑 Switch 游戏，路线有三条：模拟器（Ryujinx 这类，快但兼容性看天）、兼容层（转译，稳但有一层税）、真·原生（AOT 重编译成 x86-64，慢但体验上限最高）。这个项目押第三条：把三款游戏的 PC 重编译项目（异界锁链、战神 3 重制版、血源诅咒）搬上 Deck，做到"准原生"——Steam 平台集成、Deck 原生输入/陀螺、画面资产对齐掌机观感。

目标不是"能跑"，是**达到厂商原生移植的标准层次**。这个目标定高了，后面所有取舍才有判据。

## 三堵墙，各自怎么破

Switch 是 AArch64 + Maxwell GPU + Horizon 系统服务，Deck 是 x86-64 + Vulkan（RADV/GCN），直接搬有三堵墙：

| 墙 | 问题 | 破法 |
| --- | --- | --- |
| A：CPU 指令集 | AArch64 代码跑不了 x86-64 | LLVM AOT 重编译，把 Switch 二进制静态重译成 x86-64，运行时零解释 |
| B：GPU 着色器 | Maxwell SASS 不是 Vulkan | SASS → SPIR-V（复用 Ryujinx 的转译器）→ Vulkan，跳过 Metal 那一步 |
| C：系统服务 | Horizon 的服务调用（音频、输入、NFC） | 在宿主二进制里 HLE 重新实现，不搬 HOS 内核 |

结论是这条路线**不需要 HOS 内核、不需要 Hypervisor、不需要 TrustZone**——早期调研里"HOS 上 x86 不可能"的判断被推翻，修正后的结论才敢立项。三堵墙都有活跃的参考项目（ScarletNX、LAS Recomp、totk-recomp），项目本身做的是"把上游成果对齐到 Deck 的验收标准"，不是从零造轮子。

三款游戏的上游成熟度差异很大，这直接决定了工作量的分布：

- **血源诅咒**（bbport）：上游最成熟，原生 x86-64 执行 + 自研 Vulkan 渲染器，Deck 上 30-60fps 可用，工作重心在验收和平台集成；
- **异界锁链**（astral-chain-pc-recomp）：LLVM 静态重编译管线完整，但上游明说"尚未针对 4GB VRAM 和 Deck 优化"，这块要自己补；
- **战神 3**（SpartanPort）：上游在 Deck/RADV 上有已知的渲染损坏，动手前要先确认新版是否修掉，否则搬过去也是坏的。

## 遥操测试电池：Deck 是验收场，不是工地

这个项目最容易搞砸的地方是"在 Deck 上又改又测"——Deck 的 rootfs 是只读的（`steamos-readonly`），系统盘小、存档珍贵，重活在 Deck 上做等于边开飞机边换发动机。

工程纪律定死一条：**构建、AOT、迭代全在远端 Runner 上做；Deck 只做最终验收，且验收过程必须轻拿轻放**。落地成一个测试电池（deck-experience），每次在 Deck 上跑一轮受控会话：

- 启动走 `systemd-run --user --unit` 包一层，SSH 断了进程不跟着死（`setsid nohup` 挡不住 logind 的 cgroup 回收，这条是实测出来的）；
- 环境固化在一个 candidate 脚本里：语言、陀螺、手柄过滤、帧率开关全部显式声明，不接受"上次好像是这么设的"；
- 存储保护：bind mount 只暴露存档目录，可用空间低于 1GiB 自动停会话，会话结束写 `exit.json`，其中 `player_saves_unchanged` 是硬断言——**测完存档没被动过，这轮测试才算干净**；
- 全程留 `monitor.jsonl`：帧率、帧时、剩余空间，事后归因用。

有一轮实测的收获要单独记：某帧率解锁开关设了 `60fps`，窗口标题却稳定显示 `30.0 fps`、帧时 p50 31.9ms——开关没生效。如果只看"能跑、没崩"，这个回归就漏过去了。**验收要读到运行时数字，不是读进程活着。**

## UI 与美术资产：准原生的最后一公里

"能跑"和"准原生"之间差的是观感层，这部分工作量不显山露水但占了不少：

- **按键提示**：按 Deck 实际绑定的手柄出图标，Xbox/Nintendo 两套布局都要对，QTE 提示同步；
- **画面**：掌机分辨率下的马赛克/模糊问题逐项过，各游戏的超分路径（FSR 各版本）在 4GB 显存约束下重新选型；
- **平台集成**：Steam 的游戏库条目、封面、控制器模板，做到在 Deck 的游戏模式里"看起来就是个正常游戏"；
- **中文化**：支持简中的上游直接用，不支持的按资产管线补，不硬改字符串表。

这块的验收标准是主观的，所以定成了 63 条可勾选的案例（输入/UI/画面/系统/性能五类），外加一轮盲区审计把案例集本身也审了一遍——**验收标准也会过时，它自己也需要验收**。

## 当前的诚实状态

- 三款里血源诅咒在 Deck 上可用度最高；异界锁链的平台适配在推进；战神 3 等上游修 RADV 问题再收口；
- 全部结论 `hardware_validated=false` 的口径：代码合入、CI 绿、遥操会话跑通，都不等于"用户手里那台 Deck 上日常可玩"，最后一步永远留给人机共验；
- 中文配音（三款全量）目前停在调研：格式管线（XVAG/Wwise/FSB5）摸清了，TTS 许可和法律边界（不上传资产/模型）确认了，实施还没授权——**调研不是实施**，这条边界在知识库里单独记过。

## 这个项目在整站的位置

Deck 三部曲是"AI Agent 参与游戏工程"的样本：Agent 承担上游源码审计、验收案例生成、遥操会话编排、回归归因；人把三关——目标（准原生）、纪律（Deck 轻拿轻放）、验收（读数字不读心跳）。这个分工比例和前面几篇的 homelab 接管是同一个模式，只是对象从基础设施换成了游戏。
