前几篇把主机层的通道建完了：[Windows 走 WinRM](/2026/10/01/Windows-Servers%E7%9A%84Agent%E6%8E%A5%E7%AE%A1PowerShell7%E4%B8%8EWinRM%E5%8F%8C%E9%80%9A%E9%81%93/)，[Home Assistant 走系统层加应用层双通道](/2026/10/03/HomeAssistant%E7%9A%84%E5%86%85%E6%A0%B8%E6%8E%A5%E7%AE%A1Agent%E8%BF%9B%E7%B3%BB%E7%BB%9F%E5%B1%82/)。剩下的是量最大的一块：家里十几个 Web 控制台服务，雷池 WAF、GitLab、Zabbix、LiteLLM、WeKnora、DataEase，每个都有自己的登录页和 API，互不相通。

这块的接管原则一句话：**API 是操作面，UI 是核对面**。Agent 干活走 API，改完去 UI 对应的页面上用真实请求核对一次——因为 UI 显示和 API 返回不一致的情况，这轮里真实出现过。

## 每项服务怎么建操作面

统一做了四件事，所有服务照同一套走：

**1. API 凭据统一托管。** 每项服务的 API token/密钥单独存一个 600 权限文件，路径进 Agent 全局基线，命名规则 `~/.config/<服务>-<标识>/api-token`。不放在环境变量（会漏进日志），不放在共享配置（一个服务改密码不影响别人），脚本里读文件不回显。

**2. 探活接口固定。** 每项服务指定一个"最便宜的探活请求"（版本接口、健康检查端点），巡检只打这一个。探活失败才升级到深度检查，避免巡检本身变成对自家服务的压力源。

**3. 写操作留痕。** 所有经 API 的写操作（改规则、建用户、调策略），Agent 在执行前后各读一次相关状态，diff 写进报告。API 返回 200 不等于状态变了——雷池 WAF 上就遇到过返回成功但实际没生效的策略项。

**4. 降级路径写明。** API 不可用时走什么通道、走到哪一级算失败，每项服务写死。雷池 WAF 的降级是 SSH 进容器看日志；GitLab 是走 Runner 机器；Zabbix 是查数据库。

## 两个 API 通道救回来的故障

**雷池 WAF 的管理 API 403。** 一次 WAF 升级后管理 API 开始返回 403，UI 登录却正常。纯 UI 排查会卡在"到底是哪个权限"，走 API 逐接口二分，定位到是版本探测接口和授权接口的返回不一致——一个说社区版一个说商业版，两个接口的状态没对齐。这个不一致后来被当成已知状态记录在案，巡检里对这个接口做了豁免。

**Zabbix 的 systemd 队列死锁。** Zabbix 打补丁后 PHP 进程反复重启，systemd 的 job 队列堆死，服务"在跑但起不来"。API 层看是 `apiinfo.version` 超时，纯监控面看不出队列问题，SSH 进系统层 `pkill -9` 解除死锁后 API 恢复。这条的经验写进了故障手册：**监控面全绿的系统，系统层可能已经死锁**，探活超时时不要只看服务状态。

## 巡检节奏

固定节奏的巡检代替"出事了再查"：

- 探活轮：所有服务的最便宜探活，一轮跑完，失败项升级深度检查；
- 深度检查：只针对失败项，走各自写明的那条路径；
- 报告：每轮巡检一份，状态变化（不是全量状态）进 Agent 知识库存档。

这个节奏跑下来，真正值钱的产出不是"发现故障"，而是**故障的归因链路完整**：哪个接口、什么返回、系统层什么状态，三段都有记录，复盘不用重新翻。

## 边界：哪些不给 Agent

全部接管不是目标。明确不放的：

- **计费/配额类写操作**（LiteLLM 的 key 额度调整）：读可以，写要人工确认；
- **对外暴露的策略变更**（WAF 对公网的规则）：Agent 提 diff，人批准后执行；
- **证书签发**：频率低、影响面大，保持人工。

放与不放的分界线就一条：**错了能不能在十分钟内无痕回滚**。能，放；不能，留人工确认环节。

**遗留未闭环**：各服务的告警源还是分散的，Zabbix 只覆盖了主机层，服务层的异常（API 探活失败、队列积压）目前靠巡检轮发现，不是实时告警。统一告警面是下一步的事。
