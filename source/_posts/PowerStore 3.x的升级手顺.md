升级阵列最容易看错的是管理界面。页面切回登录屏时，升级任务可能还在跑，主机也可能仍有可用路径。反过来，界面上选了正确的包，连到阵列的主机如果只剩单路径，这一轮也不能照常开始。早年维护 PowerStore 3.x，我用这两个问题安排窗口：升级过程中业务要守住什么，什么条件下能把变更交还给业务。

这里的 PowerStore 是承载虚拟机和备份 I/O 的存储阵列。管理会话在控制面，主机从数据路径访问卷。厂商的 NDU（无中断升级）面向受支持的冗余配置，现场仍要核对多路径、告警和本次版本限制。菜单与截图保留的是当时的 3.x 版本，跨版本照搬之前先查发行说明。

## 先定升级路径

旧稿把「先升盘固件，再升系统」写成了通用顺序。Dell 的驱动器固件 FAQ 建议**先升级 PowerStoreOS，再安装与目标版本兼容的盘固件包**。开始前按设备型号、当前版本和目标版本查发行说明，确认是否需要中间版本、适用的健康检查包以及盘固件支持范围。包名里的构建号只能用来识别软件包。

Dell 还记录了一个容易漏掉的情况。部分盘固件更新在 PowerStoreOS 3.0.x 和 3.2.0.x 上可能报告成功，但实际没有更新任何驱动器。以管理界面读到的逐盘固件版本为准。[Dell 盘固件 FAQ](https://www.dell.com/support/kbdoc/en-us/000214519/powerstore-powerstore-drive-firmware-upgrades-and-frequently-asked-questions-faq)

三类包容易混在一起。PowerStoreOS 是阵列系统，驱动器固件对应具体盘型，健康检查包提供升级之前的额外检查。窗口里至少记录这四行，拿不到具体值时先补盘点。

| 要确认的项 | 开始前记什么 | 用来判断什么 |
| --- | --- | --- |
| 设备和系统 | 型号、群集中的设备数量、当前版本、目标版本 | 目标发行说明适用范围，是否要分段升级 |
| 盘固件 | 适用的盘型、对应固件包、升级前驱动器版本 | 哪些盘应该变化，哪些盘本就不在本次范围 |
| 健康检查 | 当前版本适用的检查方式、检查包版本、发现的阻断项 | 能否进入窗口，是否要先清理群集问题 |
| 主机连通 | 代表性主机、关键卷、正常路径数、最近 I/O 与告警 | 节点滚动期间能否维持访问，窗口后是否需要追查退化 |

Dell 文档区分预升级健康检查（PUHC）与 System Check。先按源版本和目标版本选检查路径，再看结果。只在控制台看到升级包处于可选状态，仍缺少健康检查和主机多路径证据。[Dell 健康检查说明](https://www.dell.com/support/kbdoc/en-us/000192601/powerstore-using-the-run-upgrade-extensions-feature-before-starting-a-powerstoreos-upgrade)

## 我怎么把兼容性检查变成维护计划

1. 记录每台设备的 OS 和驱动器固件版本、群集健康状态、关键卷的主机连接与多路径状态。对照目标版本的升级文档执行预升级健康检查。遇到阻断项，查清原因后再排期。
2. 从主机侧确认两节点的备用路径可用，并与虚拟化、备份团队对齐维护时间。把计划中的 vVol 创建、迁移和快照任务挪出窗口。具体受限操作以本次版本的升级文档为准。
3. 给管理会话切换、健康检查重跑和业务回验留时间。时间按设备数量、版本路径、现场负载及评估结果安排。盘固件阶段应单独估时，驱动器数量和 I/O 压力都会影响时长。
4. 需要抑制 Call Home 通知时，在 PowerStore Manager 的 **Settings → Support** 里按设备启用维护模式，按预计作业时长设置截止时间，结束后确认通知恢复。

[参照 Dell 的 NDU 准备指南](https://www.dell.com/support/kbdoc/en-us/000183630/powerstore-how-to-prepare-for-a-powerstore-non-disruptive-upgrade-ndu)

排程时把三段分开算。系统升级看设备数量和升级路径，盘固件看适用盘的数量与 I/O 压力，最后单留一段回验。旧记录里单设备约 1–1.5 小时是当时的系统维护估时，只供理解这次窗口。虚拟化侧提前排开 vVol 变更，备份侧确认窗口内是否有会与升级争 I/O 的任务。

## 执行顺序和检查点

当时的版本在 **Settings → Cluster → Upgrades** 上传、选择和安装升级包。点开始前重新核对设备与包版本。启用自动下载的环境也要做这一遍，真正用的是窗口里选中的包。

![PowerStore Manager 的上传入口](https://picturebed99.oss-cn-shanghai.aliyuncs.com/img/202307280941821.png "上传程序包按钮")

![选择升级文件](https://picturebed99.oss-cn-shanghai.aliyuncs.com/img/202307280941330.png "选择文件对话框")

| 检查点 | 需要确认的结果 |
| --- | --- |
| PowerStoreOS 升级中 | 从主机侧观察路径和 I/O。管理会话断开时，重连后核对升级任务和群集状态 |
| PowerStoreOS 升级后 | 所有目标节点版本正确，群集健康，主机路径恢复到基线，再进入盘固件阶段 |
| 盘固件升级后 | 在 **Hardware → Drives** 核对适用驱动器的实际固件版本，检查告警是否清除 |
| 恢复变更前 | 验证关键存储路径和代表性业务，确认支持通知恢复，再开放暂停的任务 |

面对失败先保留任务状态和告警。版本不一致、主机路径异常或健康检查阻断时，停止推进并按对应版本的 Dell 指引处理。能否回退取决于当前升级阶段和厂商支持路径，执行前就要确认。

## 三个容易误判的结果

旧维护记录提到，管理界面在切换期间可能回到登录页。先用新会话重新读取升级任务和节点状态，同时让主机侧观察同一个代表性数据存储。任务继续走、主机仍有路径且 I/O 正常，可以继续观察。出现路径全部丢失或 I/O 错误时，按业务故障处理，并保留发生时间和两侧告警，避免在原任务状态不明时重复提交升级。

盘固件的验收我会拿升级前后的逐盘版本清单对照。有目标盘没变化，就按盘型、目标包和当前 PowerStoreOS 版本往回查。升级状态为成功但没有目标版本变化，应记录为未证实写入。Dell 在部分 3.x 版本上记录过这种情况，不能用一个绿灯替代清单。

最后交接给虚拟化与备份同事三份记录。阵列版本及告警、主机路径及 I/O、代表性业务验证的时间和结果。只有前两份记录时，最多能说明存储侧恢复，维护窗口还应留到业务验证结束。

后来做虚拟化迁移、备份调整或模型数据服务时，我沿用了这个拆法。谁在看设备，谁在看主机，谁能确认一条真实业务完成，要在变更前分好。这样遇到版本绿灯、页面掉线或任务重试，值班人都有下一步可以核对。
