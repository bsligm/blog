我买 DGX Spark，是想把编码会话里的长上下文留在自己手里。模型拉起来以后，还要检查工具调用能否作为结构化事件交给客户端。我把验收分成两部分：引擎能接多长的输入、承受多少并发，以及每个客户端能否完成工具调用、压缩和续答。

## 机器与环境

本次用的是 GB10、Ubuntu 24.04.5 LTS / aarch64 和 580.178.04 驱动。[NVIDIA 官方规格](https://docs.nvidia.com/dgx/dgx-spark/hardware.html) 是 128 GB 统一内存，20 个 Arm 核心（10 个 Cortex-X925、10 个 Cortex-A725）。本机监控口径约 121 GiB，模型常驻时占用约 111 GiB，这份内存预算只能保留一个常驻模型。部署前还要检查镜像是否有 arm64 产物，我第一轮就遇到过仅提供 x86 镜像的组件。

有线与无线并存时，默认路由曾因无线重连改变。固定路由优先级后，用实际推理请求回测连通性。运行时把 KV 缓存、队列深度、内存压力和温度放在一起看，便于区分请求拥塞与宿主资源压力。

## 部署形态

服务拆成五个组件：vLLM 跑模型，LiteLLM 做协议转换和路由，PostgreSQL 保存网关状态，管理入口和 API 入口各自隔离。思考档位、system 消息、输出预算和协议错误体在 API 边界处理。

LiteLLM 的模型注册用 YAML 声明式挂载，没用控制台的数据库注册。实测路由表在 `LiteLLM_ProxyModelTable` 里是 0 行，所有路由都来自挂载进容器的那份配置文件。排查时这个区别很关键：控制台看不到模型、或控制台改了不生效，先看文件而不是怀疑数据库。配置骨架：

```yaml
model_list:
  - model_name: local-long-context        # 对外别名，与权重仓库名解耦
    litellm_params:
      model: hosted_vllm/local-long-context
      api_base: http://<vllm-host>:<port>/v1
      api_key: os.environ/DGX_API_KEY
# 家庭自用，价格全部置 0，只用于消耗记账，不参与计费
```

模型别名与权重仓库名解耦是有意的：换一次量化版本不用去改四个客户端的配置。

接线时我按三段验收。先直连引擎跑一条短请求，确认镜像、权重和输出。再用同一条输入走网关，核对模型别名和错误响应。最后接真实客户端，加入工具调用、长历史和压缩测试。这样发现输出变短时，可以从实际请求里核对是客户端缩减预算、兼容层改了字段，还是引擎提前停止。

## vLLM 参数逐条

版本 `0.1.dev20073+g8e685d198`，NVFP4 量化权重。启动命令去掉路径与无关环境变量后是这样：

```bash
vllm serve /models/candidate \
  --served-model-name local-long-context \
  --max-model-len 262144 \
  --max-num-seqs 8 \
  --gpu-memory-utilization 0.80 \
  --enable-prefix-caching \
  --enable-chunked-prefill \
  --max-num-batched-tokens 8192 \
  --kv-cache-dtype bfloat16 \
  --mamba-ssm-cache-dtype float32 \
  --limit-mm-per-prompt '{"image":64,"video":1}' \
  --tool-call-parser qwen3_xml \
  --reasoning-parser qwen3 \
  --speculative-config '{"method":"mtp","num_speculative_tokens":2}' \
  --compilation-config '{"cudagraph_mode":"PIECEWISE","splitting_ops":[...]}'
```

**`--max-model-len 262144`。** 256K 窗口。KV cache 占用与窗口长度线性相关，这一项决定后面所有并发数字。

**`--gpu-memory-utilization 0.80`。** vLLM 默认是 0.9。统一内存架构下 0.9 会挤压系统页缓存和宿主进程，早期出现过内存回收引起的请求毛刺，降到 0.80 之后没再复现。降低的是引擎的内存预算，宿主实际余量以运行时读数为准。

**`--max-num-seqs 8`。** 调度上限，不是容量声明。后文会看到真实可用并发远低于它。

**`--enable-prefix-caching`。** 收益最大的一项。Agent 多轮请求前缀高度重复（system + 工具定义 + 历史），复测时把缓存冷启动和命中后的首 token 延迟分开。

**`--enable-chunked-prefill` 与 `--max-num-batched-tokens 8192`。** 256K 窗口的长 prompt 如果整块预填充，会把正在解码的请求全部堵住。分块之后 8192 token 一批，预填充可以和已有解码任务交错调度。批大小从 4096 试到 8192，再往上首 token 延迟开始回弹。

**`--kv-cache-dtype bfloat16`。** 量化权重配 BF16 的 KV cache。这次保留 BF16。FP8 的容量、延迟和长文检索对照没有测完。

**`--mamba-ssm-cache-dtype float32`。** 本次为线性注意力的状态缓存保留 FP32，未做独立的精度对照。

**`--tool-call-parser qwen3_xml` 与 `--reasoning-parser qwen3`。** 工具调用走 XML 标记，思考内容独立成 reasoning 通道。两个 parser 配错的症状完全不同：前者是工具调用变成正文文本，后者是思考内容混进答案被客户端当成结果。

**`--speculative-config` 的 MTP，`num_speculative_tokens=2`。** 多 token 预测投机解码。2 是实测拐点：1 收益不够，3 之后接受率下降导致的回退抵消了收益。

**`--limit-mm-per-prompt`。** 多模态上限，见后文。

**PIECEWISE cudagraph 与 `splitting_ops`。** 这份开发构建使用分段图捕获。`splitting_ops` 随镜像和模型实现变化，应与版本一起固定。

权重挂载有个坑值得单列：容器内 `/models/candidate` 映射到宿主模型目录，但实际生效的 `config.json` 来自另一份实验目录里的覆盖文件。**在模型目录里改 config 不生效**，改完重启发现参数没变，第一反应会误判成版本没生效。定位方式是 `docker inspect` 看挂载表，不是看模型目录。

## 256K 其实是三个不同的数字

配置里写 262144，客户端显示 262144，真正能用的空间是另一回事。三层：

1. **引擎窗口**——262144，`--max-model-len` 决定的硬上限。
2. **有效聊天空间**——要减掉固定开销。实测固定前缀 28.5K token：system prompt 8.6K、工具定义 17.5K、skills 2.4K。
3. **压缩触发点**——网关侧阈值 130K，实际触发点约 123.5K。

第二层是踩坑踩出来的。最初压缩阈值设 100K，压缩频率约 23 次/小时：100K 阈值减掉 28.5K 固定开销，只剩 71.5K 真正留给对话，两三轮工具调用就触发一次。调到 130K 之后降到约 13 次/小时，安全校验是 123.5K 触发点加 65.5K 输出预留等于 189K，仍小于 262K。

即便如此，前缀本来就有 80-100K 的重会话仍然每 7-12 分钟压一次。这是结构问题，没调干净。

另有一条被推翻的假设值得记一笔：最初按"tokenizer 计数存在 25% 偏差"做过修正，后来判定这个修正本身不严谨——不同模型的 tokenizer 行为不同，正确做法是拿真实 token 数实测，而不是套一个比例系数。

## 如何复测长上下文

固定引擎镜像、权重和分词器版本，用合成文本在开头、中段和近末尾插入随机标记。让客户端一次返回三个值，逐项做严格匹配。输入长度从实际发出的请求统计，包括 system 消息、工具定义与历史。固定前缀和更换前缀分别测，留首 token 时间、生成速度和实际输入用量。

原有用例做到 250046 个输入 token，三个标记全部读回。这一轮覆盖的是长输入的定位任务。要评估摘要、跨段推理或长会话工具调用，每个任务需要单独的判据。

## 两路样本充足，三路只有一个瞬时点

从引擎调度日志采了 7983 条样本。

| 并发 | 吞吐 | 样本情况 |
| --- | --- | --- |
| 1 路 | 28.3 token/s（单路中位） | 充足 |
| 2 路 | 40.9 token/s（合计） | 充足 |
| 3 路 | — | 仅 1 个瞬时样本，KV cache 86.2% |

**持续 3 路并发可用这件事没有被证明。** 所以我不会写"这台机器支持 3 路并发"。网关侧并发门禁按 3 设置，是留了保守余量的。把 `max-num-seqs=8` 当 SLA 是这类部署最容易犯的错误：它只表示引擎最多愿意同时排 8 个序列，不表示 8 路都有可用延迟。

24 小时账本记下 570 次成功、6 次失败，端到端 P95 为 239.58 秒。另一份客户端日志记录了 104 条本地限流拒绝和 22 次压缩取消，两处统计边界不同，不能直接相加。P95 包含队列、压缩和推理等待，现有数据不足以拆出引擎延迟。外部链路的 502 单列，原因尚未定位。

要在另一台机器上给出容量结论，我会把实际输入长度、输出预算、采样参数和缓存条件固定下来，独立跑单路、双路、三路。预热结束后开始计数，分别记进入网关、进入引擎、首 token 和最后一个 token 的时间。报告里分列排队、首 token、总耗时、单路和合计吞吐、错误和取消。这轮的调度日志反映的是日常负载，持续三路仍需要受控测试。

## 四类 Agent 的接入差异

四个客户端走三种协议。Codex 和 WorkBuddy 做了客户端端到端测试，Claude Code 和 dsh 的验收停在协议层和配置层。

| Agent | 协议 | 关键配置 |
| --- | --- | --- |
| Codex | Responses | `wire_api="responses"` 加自定义头 `X-Qwen-Profile` |
| Claude Code | Anthropic Messages | 全部走环境变量 |
| WorkBuddy | Chat Completions | `base_url` 加模型名 |
| dsh | Chat Completions | 两个 compat 开关 |

**Codex** 走 Responses API。除 `base_url`、`env_key` 外必须显式声明三项窗口参数：`model_context_window=262144`、`model_auto_compact_token_limit=131072`、`tool_output_token_limit=8192`。第一项客户端会按模型名猜，猜错直接超窗；后两项不写的话一次工具输出就能把整个历史撑爆，实测有过 584098 字节的单次工具输出进历史。压缩走原生 `POST /v1/responses/:compact`，需要在边界代理白名单里单独放行。

**Claude Code** 的协议兼容性使用环境变量配置，网关地址与模型别名分别设置：`ANTHROPIC_BASE_URL`、`ANTHROPIC_MODEL`、`ANTHROPIC_DEFAULT_OPUS_MODEL`、`ANTHROPIC_DEFAULT_SONNET_MODEL`、`ANTHROPIC_DEFAULT_HAIKU_MODEL`，凭据走 `ANTHROPIC_AUTH_TOKEN`。网关侧也要核对协议版本头和错误响应。缺少错误体里的 `type: "error"` 时，客户端只显示通用提示。

**WorkBuddy** 最省事，标准 OpenAI Chat Completions，给 `base_url` 和模型名就通。

**dsh**（DeepSeek Harness）需要两个 compat 开关：`supportsDeveloperRole: false`，发 developer 角色会被模板拒；`maxTokensField: max_tokens`，默认发的 `max_completion_tokens` vLLM 侧不认。还要显式声明 `contextWindow: 262144` 与 `maxTokens: 32768`，**这两个数字不能都填 262144**——输出上限等于上下文窗口时，客户端侧的压力校验直接抛错。

ZCode 也接过，同样要显式指定窗口（它按官方模型名做能力匹配，会把本地 262K 当云端 1M 处理），后来退出了验收范围。

**边界说明**：Claude Code 与 dsh 在这台机器上没有真机安装，只做到协议层与配置层验证。真机端到端跑通的是 Codex 与 WorkBuddy。总验收口径：协议转换用例 57/57、parser 用例 57/57、真实客户端用例 32/32，250046 input token 下三处位置标记全部识别正确。

复测时我会先接一个无副作用的工具，例如输入整数并返回它的平方。看模型是否识别该工具、客户端是否拿到结构化调用、执行结果能否带回会话、模型是否正常续答。流式用例再检查参数片段能否拼回合法 JSON。把同一用例在协议脚本和真实客户端分别执行，协议兼容和客户端可用性各有自己的记录。

## 思考档位映射

本次使用的引擎配置接受 low / medium / xhigh 三个档位。直接传入未支持的档位曾返回 400，网关按以下规则归并：

```text
none / minimal / low       →  low
medium                     →  medium
high / xhigh / max / ultra →  xhigh
```

映射的代价是"界面显示八档、实际三档"，这是等价性的真实损失，得承认。它比另一种做法好：白名单外一律 400，客户端直接不可用。

围绕档位还有三个坑。

**`extra_body` 与顶层不等价。** LiteLLM 1.101 对两条载体的合并优先级不一致，表现为"显式关闭思考但仍在思考""low 变成了 xhigh"。修法是在代理层统一顶层与 `extra_body` 里的 `reasoning`/`thinking` 载体，并固定优先级：现代 effort 语义优先，显式关闭优先。

**legacy `budget_tokens` 不能真限流。** 旧的 Anthropic 思考预算被直传采样器，思考会被硬截断。处置是它只作强度提示，走 1024/2048/4096 的既有阈值映射，不进采样器。语义上不完全等同于原预算上限，属于已知妥协。

**`null` / `default` 必须显式拒绝。** 客户端会发可选等级的空值，落到引擎是隐式行为。代理层直接返回 400 并列出可取值，比让它静默降级好排查。

`max_tokens` 缺失也要补。客户端省略时上游不会自动补，表现为随机截断。代理补 `max_output_tokens = max(default_output, budget + 8192)`，并硬校验输出上限在 1 到 262144 之间、思考预算不小于输出上限，否则 400。

system 消息重排是另一处必改。Qwen 的 ChatML 只接受单条前导 system，新客户端会发多条 system/developer。代理把它们合并置顶，非文本 content 一律拒 400 而不是静默字符串化——静默字符串化会把多模态内容变成一串看不出问题的 JSON 文本，问题会推迟到很后面才暴露。

## 压缩队列隔离

有一段时间每天出现 77 个最终 400。根因是"只接受摘要、拒绝 `tools` 的压缩服务"被放进了普通推理的回退链：普通请求打进去被拒，压缩请求带着 `tools` 打进去也被拒。

修复方式是把两个入口彻底分开：普通恢复与摘要各自独立 provider、独立并发槽，底层同一个上游服务，靠 provider 维度做队列隔离。之后做了故障注入验证——两个压缩任务正在跑时，普通恢复请求 0.8 秒完成、零排队；分离之前同样的注入下是 75 到 134 秒。

这个数字的口径必须说清楚：**它是故障注入结果，不是长期生产统计**。它能证明隔离有效，不能证明日常延迟就是这个水平。同轮更可靠的证据：分离之后 133 次真实请求全部 200，路由未就绪 0 次。

配套还修了几处压缩阈值的查找问题：成员带固定后缀时，查找需要 provider 通配才能命中；分组级覆盖在新版本里被忽略（实际取成员最小值），不生效的 `group/*` 覆盖要删掉，按成员阈值落实并读回。

## 多模态：把识图关到专用路由

一开始让所有路由都能识图，结果免费池的 502 拖垮主链，视觉请求跨供应商回还造成上下文污染。最终策略三条：

- **全局跨供应商识图关闭**，只保留已验证具备原生视觉能力的成员。
- **识图集中在一个专用路由组**，成员全部降档到最低思考强度。识图不需要深度思考，档位降下来吞吐差别明显。
- **图片 URL 抓取不跟跳转、不吃环境代理**（`follow_redirects=False`、`trust_env=False`），避免 SSRF 与环境代理污染。

换到专用组之后，此前某个上游累计 138 次的视觉 EOF/502 完全停止，识别请求由专用组接管，基本全部成功。

引擎侧硬上限是单请求 64 张图，65 张直接 400。已验通过的组合：64 张 512px（三种协议）、64 张 1024px、4 轮历史各 16 张。被拒之后引擎本身健康，不是崩溃。代理层不做额外的图片裁剪或降采样，把上限交给引擎是更省事也更诚实的做法。

## 接入验收也要测拒绝路径

接入测试记录 401 的来源，确认由预期的鉴权层返回。验证分三段：合法请求交给推理服务，未授权请求被拒，错误体能被客户端识别。成功拿到流式结果或工具调用以后，才记作业务通过。

## 其他几个坑

- **CLI 的写副作用比预期大。** 一条切换分组的命令会删掉客户端配置里的 provider 段和模型目录引用。每次操作后必须读回配置，不能假定"命令返回 0 就只改了该改的"。
- **直接改 JSON 配置会被覆盖。** 编排层的配置有内存态，手工写入的字段会在下一次保存时被覆盖，规则变更必须走 CLI。
- **shell 语法坑。** `变量名:low` 在 zsh 里会被当变量修饰符吞掉，必须写 `${变量名}:low`。这类错误的表现是规则静默失效，很难查。
- **设置命令的隐藏语义。** 一处"设置分组"操作会清空该分组的规则，所以每次设置后需要重新加规则。
- **嵌套分组带档位后缀是非法语法**，导致路由被标记为未就绪，186 个探针里命中 11 次。
- **客户端进程会缓存旧模型目录**，改完配置显示的还是旧窗口值。正确处置是读回网关实际版本，而不是中断活跃任务去重启客户端。
- **流式中断不做跨模型拼接。** 半截响应跨模型续拼会产生脏内容，策略是流已经开始就不换上游，4xx 原样返回。
- **回滚脚本默认只读。** 校验通过才允许 `--apply`，并拒绝未知漂移。回滚脚本默认执行恢复是一件很危险的事。

## 仍然没解决的问题

- **持续 3 路并发未验证。** 要做受控压测才能给出容量结论。
- **公网 502 根因未闭环。** 影响面小，但没定位。
- **重会话压缩频率仍偏高。** 前缀 80-100K 的会话每 7-12 分钟压一次，固定开销结构决定的，不是参数能解决的。
- **内存余量偏紧。** 111/121 GiB 常驻，想加第二个模型必须先解决这件事。
- **单机单点。** 所有 Agent 都指向它，它挂了就全部回退订阅 API，而这个回退目前是手动切换。

## 验收到哪一步

256K 是引擎窗口，250046 个输入 token 的三处标记都读到了。单路中位吞吐 28.3 token/s，两路合计 40.9 token/s。两类客户端通过端到端验收。重会话压缩、三路持续并发和故障后自动切换，仍需分别测。
