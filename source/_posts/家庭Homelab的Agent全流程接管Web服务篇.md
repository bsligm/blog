一次补丁窗口后，监控自己的版本查询超时了。我先查 Zabbix 和数据库的服务状态，多读几遍也没有新信息。最后把检查点挪到 systemd 作业队列，才发现数据库和监控服务还在等启动作业。这次监控告警留给我的问题很具体：接口查不通时，下一个检查到底要验证什么？

`systemctl status` 给的是某个服务的当前状态，`systemctl list-jobs` 才能列出尚未完成的启动、停止等作业。数据库没完成状态切换时，复读单个服务只会得到近似一张快照；盲发更多启动请求还会扰乱判断。当时接口超时只把我带到了故障门口，启动为什么没走完，得查系统层作业再决定怎么处理。

那次从发现异常到恢复约 67 分钟。切到作业队列定位之后，诊断加处置约 3 分钟。处理完成后，我重跑了一开始超时的同一个版本查询，确认 API 恢复响应。这一步验证的是接口可用，采集恢复还应看监控数据有没有继续更新。两段时间说的是同一次故障的两个区间，不能拿来承诺下次恢复耗时。

## WAF 的拒绝单独处理

另一次升级后，WAF 控制台能打开，管理 API 却返回 `403`。页面能登录只验证了页面的会话，管理请求能否执行还取决于那条接口的授权。看到拒绝时，我保留失败请求的时间、状态码和版本信息，把问题缩到受影响的管理请求，再对该版本文档和已有授权。只凭 `403` 推不出具体是哪个配置造成的，也不能据此判定转发受影响。

这样两个故障的下一步就分开了。版本查询超时，去查服务依赖和作业队列；管理请求被拒，先停在授权边界并记下待核项。测 WAF 的转发和规则则要走各自获准的流量路径。巡检结果里保留这些区别，才能让下一班的人看到一个可接手的问题，而不是一条泛称「异常」的告警。

## 日常巡检留下的四个字段

这两个故障之后，我给每项服务留下四条记录：

| 字段 | 平时怎么用 |
| --- | --- |
| 探活请求 | 选一个低成本、无副作用的请求，能说明该接口确实在响应 |
| 深查入口 | 查日志或系统作业队列，写清什么时候需要人接手 |
| 变更证据 | 保存变更前后状态，必要时用实际业务请求再核一次 |
| 授权范围 | 标清只读与可写操作。公网策略、证书、配额等变更保留人工审批 |

Agent 平时把探活失败的服务列出来，带上对应的系统层状态和最小证据，省去逐个打开控制台翻记录。权限和凭据跟着服务授权走，巡检输出只留状态与必要上下文。这个做法适合定期巡检，当时还没有建设统一的服务层实时告警。因此故障可能先发生、下一轮才被发现，表里的检查结果也只对记录的时间窗口负责。

我采用三段式巡检：第一轮对每项服务只打一个无副作用请求，第二轮只深查有异常的项，最后把观察值和判断一起记录。拿它接其他自托管服务时，稳定的是轮询和留证据的方式，具体探活和深查入口还要重选。版本接口适合确认服务能对话；若目的是验证知识库还能答题，探活之外要加一个能回读结果的业务请求。

下面是 Zabbix 这次的脱敏记录示意。把最初症状、下一步的证据和处置后复测分开，交给别人时可以直接从最后一个已确认状态接着查。

```yaml
component: monitoring
first_check: api version request
first_result: timeout
system_observation: database and monitoring jobs waiting
repeat_result: api responded after queue unblocked
separate_check: recent metrics still need verification
```

以后遇到同样的故障，我会从受影响的主机选一个固定间隔采集的监控项，记下恢复操作前最后一个样本时间，等一个完整采集周期加预留延迟，再查历史里是否出现晚于处置结束的新样本。如果看到了新数据，还要确认值符合预期且监控项没有进入不支持状态。若没有新样本，沿采集器、队列和入库状态往下查。原笔记可以证实版本请求恢复，没有可对账的采集样本，因此不能把约 67 分钟写成监控数据也恢复的用时。

同一表格用到 GitLab 或知识库时，探活字段仍然便宜，深查字段则换成对应服务能回答的那一个问题。读取得到权限拒绝就按拒绝记录，写操作涉及权限或公网入口则走人工审批。这样巡检不用携带一份能管理所有服务的凭据，也不会把一条绿色 API 结果误抄成整项服务健康。
