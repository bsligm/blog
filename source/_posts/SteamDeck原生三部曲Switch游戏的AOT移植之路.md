Steam Deck 上跑 Switch 游戏，路线有三条：模拟器（Ryujinx 这类，快但兼容性看天）、兼容层（转译，稳但每帧交税）、真·原生（AOT 重编译成 x86-64，慢但体验上限最高）。这个项目押第三条：把三款游戏的 PC 重编译项目（异界锁链、战神 3 重制版、血源诅咒）搬上 Deck，做到厂商原生移植的标准层次。定位先写清楚，防止后面口径漂移：**个人使用 + 自媒体 demo，不上传私有游戏资产**。目标定高，取舍才有判据；边界定死，"不做什么"才有判据。

## 三堵墙：挡的是架构差，不是单点难度

Switch 是 AArch64 + Maxwell GPU + Horizon 系统服务，Deck 是 x86-64 + Vulkan（RADV/GCN），直接搬有三堵墙：

| 墙 | 问题 | 破法 |
| --- | --- | --- |
| A：CPU 指令集 | AArch64 代码跑不了 x86-64 | LLVM AOT 重编译，把 Switch 二进制静态重译成 x86-64，运行时零解释 |
| B：GPU 着色器 | Maxwell SASS 不是 Vulkan | SASS → SPIR-V（复用 Ryujinx 的转译器）→ Vulkan，跳过 Metal 那一步 |
| C：系统服务 | Horizon 的服务调用（音频、输入、NFC） | 在宿主二进制里 HLE 重新实现，不搬 HOS 内核 |

结论是这条路线**不需要 HOS 内核、不需要 Hypervisor、不需要 TrustZone**——早期调研里"HOS 上 x86 不可能"的判断被推翻，修正后才敢立项。三堵墙都有活跃的参考项目（ScarletNX、LAS Recomp、totk-recomp），本项目不是从零造轮子，做的是"把上游成果对齐到 Deck 的验收标准"。

## 上游成熟度：工作量分布在上游，验收标准在自己

三款游戏的上游成熟度差异很大，直接决定工作量分布：

- **血源诅咒**（bbport）：上游最成熟，原生 x86-64 执行 + 自研 Vulkan 渲染器，Deck 上 30-60fps 可用，工作重心在验收和平台集成；
- **异界锁链**（astral-chain-pc-recomp）：LLVM 静态重编译管线完整，但上游明说"尚未针对 4GB VRAM 和 Deck 优化"，这块要自己补；
- **战神 3**（SpartanPort）：上游在 Deck/RADV 上有已知的渲染损坏，动手前先确认新版是否修掉，否则搬过去也是坏的。

拆开理由是**验收标准三作共用一套，不是各自"能跑"**。标准落成客观部分：63 条可勾选的案例（输入/UI/画面/系统/性能五类），外加一轮盲区审计把案例集本身也审了一遍——**验收标准也会过时，它自己也需要验收**。

## Deck 是验收场，不是工地

这个项目最容易搞砸的地方是"在 Deck 上又改又测"——Deck 的 rootfs 只读（steamos-readonly），系统盘小、存档珍贵，重活在 Deck 上做等于边开飞机边换发动机。

纪律定死一条：**构建、AOT、迭代全在远端 Runner 上做；Deck 只做最终验收，且验收过程必须轻拿轻放**。落地成一个测试电池（deck-experience），每次在 Deck 上跑一轮受控会话：

- 启动走 `systemd-run --user --unit` 包一层，SSH 断了进程不跟着死（`setsid nohup` 挡不住 logind 的 cgroup 回收，这条是实测出来的，不是查出来的）；
- 环境固化在一个 candidate 脚本里：语言、陀螺、手柄过滤、帧率开关全部显式声明，不接受"上次好像是这么设的"；
- 存储保护：bind mount 只暴露存档目录，可用空间低于 1GiB 自动停会话，会话结束写 `exit.json`，其中 `player_saves_unchanged` 是硬断言——**测完存档没被动过，这轮测试才算干净**；
- 全程留 `monitor.jsonl`：帧率、帧时、剩余空间，事后归因用。

## 反直觉的坑：60fps 开关设了，窗口标题写着 30.0

TOTK 的帧率解锁开关设了 `60fps`，窗口标题却稳定显示 `30.0 fps`、帧时 p50 31.91ms——开关没生效。反直觉的地方：没有报错、没有崩溃、帧曲线还很稳，"能跑、没崩"恰恰是最容易骗过去的判据。这条回归靠 monitor 日志里的运行时数字读出来的，不读数字就漏过去了。

## UI 与美术资产：准原生的最后一公里

"能跑"和"准原生"之间差的是观感层，工作量不显山露水但占了不少：

- **按键提示**：按 Deck 实际绑定的手柄出图标，Xbox/Nintendo 两套布局都要对，QTE 提示同步；
- **画面**：掌机分辨率下的马赛克/模糊问题逐项过，各游戏的超分路径（FSR 各版本）在 4GB 显存约束下重新选型；
- **平台集成**：Steam 的游戏库条目、封面、控制器模板，做到在 Deck 的游戏模式里"看起来就是个正常游戏"；
- **中文化**：支持简中的上游直接用，不支持的按资产管线补，不硬改字符串表。

## 小结

三堵墙都是上游破的，本项目实际做的是验收对齐：遥操电池、63 条案例、存储硬断言。真正花时间的仍是文档不写的部分：Deck 只读 rootfs 逼着构建远端化、logind 的 cgroup 回收让 `setsid nohup` 失效、60fps 开关不生效还不报错。这也是"AI Agent 参与游戏工程"的样本：Agent 承担上游源码审计、验收案例生成、遥操会话编排、回归归因；人把三关——目标（准原生）、纪律（Deck 轻拿轻放）、验收（读数字不读心跳）。和前面 homelab 接管那几篇是同一个模式，只是对象从基础设施换成了游戏。

只留一条经验：**Deck 的验收要读运行时数字，不是读进程活着。**
